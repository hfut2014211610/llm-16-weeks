### 第 2 周补强：MLP、初始化、激活函数、BatchNorm（12 页）

`python mlp2.py`，CPU 约 2 分钟，用 names.txt 训练模型造名字。

| 看点 | 实测 |
|---|---|
| bigram → MLP | dev 2.4533 → 2.1410 |
| 初始化没做好 | 初始 loss 25.8（应当是 3.30），tanh 饱和 62.6% |

### 第 2 批：把 GPT 改成 Llama（13 页）

每个改动都能单独开关，在 CPU 上跑 3000 步对比：

| 累积改动 | 参数量 | val loss |
|---|---|---|
| GPT 基线 | 211,777 | 1.7755 |
| + RMSNorm | 211,201 | 1.7846 |
| + RoPE | 207,105 | 1.6727 |
| + SwiGLU | 208,481 | 1.6631 |
| + GQA（4 个 Q 头共用 2 个 KV 头） | 192,097 | 1.6737 |
| + 去掉 bias = 完整 Llama | 190,144 | 1.6901 |

- 几乎全部收益来自 RoPE。其余几项的差距比“只换随机种子”的波动（0.035）还小，它们本来是为省显存、省计算和训练稳定设计的。
- GQA 把每个 token 的 KV cache 减半。换到 Llama-3-8B 上，8K 上下文时 KV cache 是 1 GiB，普通多头注意力要 4 GiB。
- 第 7 章把参数名对应到 HF config.json 字段和 GGUF/llama.cpp 里的名字（`n_head_kv`、`freq_base`、`rms_norm_eps`），用 Ollama 时看日志就能对上。

完成标准：跑通 `llama.py` 和消融实验，用自己的话讲清四个改动各解决什么问题。

### 建议顺序

### Meta 的“瘦编排器”：让路由器少干活，agent 反而更可靠
Meta 给数据管道 agent 做了约 1300 行的确定性编排器，只负责分类意图、收集字段、可靠性检查，把 20+ 工作流分派给 14 个上下文隔离的专项子 agent，自己不做领域推理。单个“全知”agent 上下文超过阈值后反而变差；新列接入配置从手工 3–4 天缩到不到 1 小时，新用例只需新增工作流模板。与 harness 工程相关：确定性决策留给代码、概率性推理放进隔离上下文。
